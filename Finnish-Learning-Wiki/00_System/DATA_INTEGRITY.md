# DATA INTEGRITY

## Цель
Не допускать потери, дублирования или тихого перезаписывания учебных данных.

## Обязательный цикл изменения
Перед любым изменением данных использовать:

**Read → Compare → Merge/Update → Write → Verify**

1. **Read** — сначала прочитать текущую версию файла.
2. **Compare** — определить, новая ли это запись, продолжение существующей сессии или конфликт.
3. **Merge/Update** — сохранить полезные существующие данные; не затирать их вслепую.
4. **Write** — записывать только после проверки актуального SHA файла.
5. **Verify** — после записи перечитать изменённый файл и проверить результат.

## Файлы с одинаковой датой
Дата не является уникальным идентификатором сессии.

Если в один день было несколько занятий, использовать один дневной файл с отдельными блоками:

```text
# 12 августа 2026

## Session 1 — morning
...

## Session 2 — evening
...
```

Не создавать `2026-08-12_v2.md`, если можно сохранить несколько сессий в одном дневном файле.

## Конфликты
Если существующий файл и новые данные относятся к одной сессии:
- объединить информацию;
- не удалять старые метрики, ошибки или retention без причины;
- при необходимости явно отметить, что данные были уточнены.

Если это разные сессии одного дня:
- сохранить обе как отдельные блоки;
- не смешивать метрики и ошибки между ними.

Если версии содержат противоречивые метрики и невозможно определить правильную:
- не выбирать молча;
- сохранить обе версии с контекстом/временем;
- отметить конфликт для последующего разбора.

## Источник истины
`Current_State.md`, `Today.md` и `Retention_Dashboard.md` должны отражать последнюю **подтверждённую** сессию, а не просто последнюю изменённую дату файла.

## Безопасность записи
- Никогда не перезаписывать существующий файл без предварительного чтения.
- Не обновлять файл по устаревшему SHA.
- Если файл изменился после чтения, перечитать его и заново выполнить Compare → Merge.
- После записи обязательно проверить содержимое.

## История
Каждое существенное обновление должно быть понятно по Git commit message: что изменено и почему.

## Принцип
**Сохранить историю лучше, чем упростить структуру ценой потери данных.**
